02

Telegram 侧的原语

Telegram 提供的不是「支付」，而是消息、按钮回调和网页入口。骗子把它们组合成「客服感」和「官方感」。

原语真实机制本案用法可核对点
Bot@BotFather 创建，拿到 token；bot 是 is_bot=true 的账号，可以发消息、编辑、删除、置顶，但不能创建群、不能冒充成员。「云上商铺」「Okpay」「鱼苗通知」都是 bot。点名字看资料；bot 有 BOT 标记，没有官方认证勾。
群 / 频道群有成员、管理员、入群服务消息；频道有订阅者、浏览量，一般只能管理员发言。群负责晒单和「官方客服」，频道负责放长文、截图和「战绩」。群可公开加入；频道可转发；两者都能被举报。
inline_keyboard消息附带按钮数组；每个按钮是 callback_data、url 或 web_app。「收款」「提币」「立即支付」「联系客服」。按钮文字不等于动作；点下去看跳到哪里。
callback_query用户点按钮 → Telegram 把 callback_query（含 data、from、message_id）推给 bot 服务器；bot 必须 answerCallbackQuery。点「收款」后，bot 知道是谁、点了哪张卡、哪条消息。这一步没有链上交易，只是 bot 收到一个事件。
editMessageTextbot 可以改自己发过的消息，重新渲染文字和按钮。同一张卡从「待支付」变「已支付」；从「转账」变「领取成功」。「消息变了」不等于「钱到了」。
web_app 按钮在私聊里打开 Telegram Web App；只对私聊有效，群聊不可用。本案更多用 url 按钮打开外部站点，而不是 WebApp。WebApp 也要看域名和 initData 校验。
url 按钮打开内置浏览器；首次会弹「打开链接 / 您确定要打开此链接？」。「立即支付」「点击前往绑定」「开始验资」。这个确认框本身就是「你要离开 Telegram」的提示。
inline mode / via用户在任意聊天输入 @bot 关键词，bot 返回结果，以「via @bot」署名发在当前聊天。群里的订单卡以 via @yunshang_bot 出现，看起来像官方发的。via 是「谁生成」，不是「谁担保」；群管理员可以是另一个账号。
转发 / 置顶转发保留来源；管理员可置顶。置顶「新人必读」；从频道转发「鱼领取后提现发起授权」。置顶可以删改；转发头也是内容的一部分。
社会证明头像、昵称、简介、共同群组、入群消息、反应、浏览量、晒单图。「刚提 10000U 秒到」「已到账」截图、管理员红字、群成员起哄。截图可伪造；余额可 P；看链上 txid，不看截图。
私聊客服bot 不能主动私聊未启动它的用户；普通账号可以。群里说「客服不会主动私聊你」，随后一个「小美」来私聊。私聊账号是不是群管理员？用户名是否一致？
真实 Telegram 的能力边界：bot 不能创建群，不能冒充群成员，不能伪造「官方认证」勾，也不能在没有用户先发起的情况下私聊。因此真实案件里，假群、托、晒单需要真人账号参与；本仿真把这些「社会证明」做成可回放的本地素材，而不是去注册假账号。

真实案件里通常怎么搭

1 · 账号与群

先把「场子」搭起来

买/养账号，建群和频道，设置名称、头像、简介、置顶规则；拉几个托发晒单、抢红包、说「已到账」。这一步用的是真人账号，不是 bot。

2 · 机器人

BotFather 建 bot

拿 token，部署后端（webhook 或长轮询），写菜单、商品、订单、回调；用 editMessageText 更新订单状态，用 callback_data 区分按钮。

3 · 仿站

域名 + 前端 + 钱包 SDK

注册域名、配 HTTPS、仿 UI；后端存余额/订单；前端接钱包连接和 approve 请求。页面要看起来像官方，但域名不是。

4 · 话术

把授权包装成提现

红包/订单引流 → 提现/验资 → 绑定钱包 → 授权。客服私聊、限时、原路退回、通道维护，都是为了让签名发生。

5 · 监控

indexer + 队列 + bot

订阅 Approval/Transfer，余额到阈值就归集；用 Telegram bot 通知操作者。也可以人工看余额再转。

6 · 反侦察

轮换与拖延

换域名、换账号、删消息、限制评论；受害人发现后用「风控/补钱」拖延。这些是运营手段，不是技术魔法。

实现栈（真实案件常见组合）：bot 后端 Python/Node + PostgreSQL/Redis；webhook 或长轮询；仿站 React/Vue/静态页 + TronLink/WalletConnect；支付用聚合支付、个人收款码或链上地址；监控用 TronGrid/TronScan API + 队列 + worker；通知用另一个 Telegram bot。具体技术选型因团伙而异，本案材料没有公开后台代码。
03

Okpay 线：每个页面干什么

这条线的核心不是「假钱包做得多像」，而是把一次授权拆成五个看起来正常的小步骤：领红包 → 看余额 → 提现 → 绑定钱包 → 授权。

① 钱包卡Okpay 私聊 · 19:41
真实：bot 用 sendMessage 发一条带 12 个按钮的消息；余额字段来自 bot 数据库。
仿真：静态卡 + 网格键盘，数值由 data.js 写死，领取后由 flows.js 改 wallet.usdt。
破绽：这不是钱包 App；余额是 bot 自己写的，不是链上 balanceOf。
② 转账卡「转账给你 1.00 U」
真实：一张带 callback_data 的消息卡；「收款」只是按钮，不是链上收款。
仿真：data.js 的 card:'transfer'，按钮 action okpay:claim。
破绽：没有 txid，没有付款方地址；「请在24小时内领取」是话术。
③ 领取结果10000 USDT
真实：bot 收到 callback → 数据库写 balance → editMessageText 改成「领取成功」。
仿真：claim() 追加 grant 卡，并同步钱包卡为 10,000。
破绽：只改页面状态；没有 Transfer 事件，没有交易哈希。
④ 提现「请回复要提现的金额」
真实：仿站 API 返回「需绑定钱包」，把用户导向外部 /wallet/bind。
仿真：askWithdraw() → submitWithdraw() → 消息里的「点击前往绑定」。
破绽：真提现不需要 approve；这一步是「提现」改名为「绑定」。
⑤ 绑定页okpay-app.xyz
真实：独立域名 + 钱包列表 + 「连接钱包」；钱包弹窗由 dapp 构造请求。
仿真：webpages.js 的 bindPage()，URL 栏显示域名；「连接钱包」打开假 TronLink。
破绽：域名、证书签发时间、WHOIS；页面再像也不在官方域名下。
⑥ 钱包连接TronLink
真实：WalletConnect / 深链 / WebView 唤起钱包；第一步只给地址和余额读取权限，通常不直接转钱。
仿真：openWallet({kind:'connect'})，列出「查看地址 / 查看余额 / 请求签名」。
破绽：连接本身不是转账，但它是下一步签名的入口。
⑦ 授权approve(spender, 无限)
真实：钱包展示 to=USDT 合约、data=approve(...)、spender、额度；用户签名后广播，链上只产生 Approval，不转币。
仿真：openWallet({kind:'approve'}) 显示授权对象、额度、矿工费、合约和原始请求。
破绽：「授权额度」不是「付款金额」；无限额度 = 把转出权交出去。
⑧ 账单平台余额 vs 链上
真实：仿站自己做一份「账单」，平台余额和链上记录是两套账。
仿真：showLedger() 显示「平台余额 +10,000 / 链上收款 暂无记录」。
破绽：这就是最该截图的一页：页面余额有数，链上没流水。
⑨ 验资第二次授权
真实：客服以「首次提货 1:1 验资」为由，再调一次钱包，构造第二笔 approve（1,000 USDT 或新 spender）。
仿真：verifyPage() + verifyApproved，复盘标记「授权额度 ≠ 付款」。
破绽：「验资款原路退回」在链上没有对应交易；要签的仍是额度。

仿站怎么伪造余额？

仿站只需要一个数字字段。页面余额可以存在前端状态、localStorage、会话或数据库里；链上余额只能由 TRON 节点的 balanceOf 和 Transfer 事件决定。这两个数字没有任何自动同步关系。仿站写 10,000，只是把 10,000 写进自己的账本。

// 仿站自己的一本账（示意，来自本仿真 flows.js） state.okpay.balance = 10000; // 页面数字 state.okpay.balanceShown = '10,000.00'; // 卡片/账单读它 // 链上真实情况（仿站不会给你看） // token.balanceOf(victim) === 0 // 没有 txid，没有 Transfer 事件
核证动作：打开区块浏览器，按地址查 TRC20 的 Transfer；或让平台给出 txid。拿不出 txid 的「到账」，都只是页面文字。
04

为什么授权后会被盗

因为签的不是「付款」，而是「允许某个地址在额度内转走我的 USDT」。这是 TRC20 标准里的 approve，不是 transfer。

1

连接钱包

dapp 拿到地址和余额读取权限。此时通常还不能动钱。

2

构造交易

dapp 构造一笔发往 USDT 合约的交易：to = USDT 合约，data = approve(spender, amount)。收款地址不是「付款对象」，而是代币合约。

3

钱包展示并签名

钱包把合约、spender、额度、矿工费展示给用户。用户点确认，钱包用私钥签名并广播。私钥没有离开钱包。

4

链上只出现 Approval

交易成功后，USDT 合约记录 allowance[你][spender] = 额度，并发出 Approval 事件。你的余额不变，所以「签完看起来没事」。

5

等钱进地址

之后你收到一笔 USDT（提现、转账、工资、另一场骗局），地址余额变大。spender 不需要你再签名，因为额度已经写进合约。

6

transferFrom 扫走

归集器调用 USDT 合约的 transferFrom(你的地址, 收款地址, 额度)。合约检查 allowance 足够，就把币转走，发出 Transfer 事件。

7

余额归零 / 提现失败

你看到「提现失败：余额不足」，或一笔不是自己发起的转出。此时 revoke 只能取消剩余额度，已经转走的币不会回来。

函数谁调用发生什么余额变化
approve(spender, amount)受害者签名设置 allowance；发出 Approval不变，只付矿工费
transfer(to, amount)受害者签名从自己地址转出减少
transferFrom(from, to, amount)spender / 归集器用 allowance 从 from 转出减少
approve(spender, 0)受害者签名（revoke）把额度清零不变，只付矿工费
无限额度为什么更危险：2^256-1 意味着以后不需要再征得你同意；只要地址里出现 USDT，spender 就能在额度内转走。有限额度也可能被全部用掉，只是上限更小。授权不是转账，但后果可能比一次转账更大。
为什么不当场扫：地址余额是 0 时扫不到东西，还会惊动你；等你进钱、放松警惕后再扫，单笔更大，也更容易被解释成「提现失败 / 通道问题」。频道里「等钱包后来进钱再处理」的说法，和这个节奏一致。

对方到底需要什么

必需

一个 spender 地址 / 合约

接收 allowance 的主体。可以是普通地址，也可以是合约；合约可以包装 transferFrom、拆分、换币。

必需

一次签名

没有受害者签名，approve 不会上链。所有页面、话术、客服，都是为了让这一次签名发生。

收割

监听 + 归集

监听地址余额/授权；用预置 TRX 付 energy；调 transferFrom；转到 collector；再换币/分流。

善后

话术与拖延

「风控」「通道维护」「再补一笔解冻」；把责任推给用户，争取时间。

06

商城线：订单、收银台、验资

商城线不是「另一个骗局」，而是同一套授权收割的引流与筛选：先用真实的小额交易建立「这是正常商店」的感觉，再把「验资」接到第二次授权上。

群与晒单社会证明
真实：群成员、管理员、晒单图、红包雨、置顶规则；用「官方」「唯一客服」制造权威。
仿真：data.js 的群消息、成员头像、fake screenshot、置顶。
破绽：晒单截图可伪造；管理员和客服可以是不同账号。
商品 Bot目录 / 下单
真实：bot 后端商品表 + 订单表；按钮带 callback_data；订单号由服务端生成。
仿真：PRODUCTS + createOrder() + order 卡。
破绽：商品、库存、发货都可以是假数据；订单号不等于发货。
收银台1.30 / 10.00 USDT
真实：外部网页；二维码指向聚合支付、个人收款码或链上地址；「正在连接支付通道」是 UI；成功页可由前端伪造。
仿真：payPage() + 二维码 + 「我已完成支付」。
破绽：域名、收款方、订单号是否对得上；付款凭证要独立流水。
客服私聊1:1 验资
真实：客服账号查订单、发链接、制造紧迫感；把公开群转到私聊，减少旁观者。
仿真：KF_MESSAGES + 付款后的 botSay + 验资链接。
破绽：「验资款原路退回」没有链上依据；提货不需要授权额度。
验资页第二笔 approve
真实：第二次调钱包，额度 1,000 USDT 或新 spender；付款与授权是两种交易。
仿真：verifyPage() + 钱包授权 + 复盘检查点 8。
破绽：页面写「验资」，钱包写「授权额度」；两个词不是一回事。
发货 / 物流拖延
真实：「仓库配货」「海关扣留」「补税/保证金」「通道维护」；继续要钱或继续授权。
仿真：客服话术与群内「已发货」；复盘把它归为拖延。
破绽：所有「再补一笔」的要求，都是二次收割。

低门槛

让你先付一笔真的

1.30 美元金额小，决策成本低；真实支付会让人觉得「这不是空壳」。

筛选

测支付能力与服从度

愿意付小钱、愿意按步骤操作的人，更可能继续走验资和授权。

沉没成本

07

这套仿真怎么实现

本仿真不是录屏，也不是静态截图拼贴，而是一个纯前端状态机：每条消息、每个按钮、每个页面都是本地 DOM/JS，没有真实网络请求。

文件职责关键技术
js/data.js会话、消息、成员、商品、订单种子声明式消息对象；buttons:[[{text, action, webapp}]]
js/ui.jsTelegram 界面渲染会话列表、气泡、回复/转发、inline keyboard、输入中、已读、主题
js/flows.js业务状态机红包领取、提现、绑定、支付、验资、快进归集
js/webpages.js仿站与钱包内置浏览器、URL 栏、收银台、绑定页、验资页、TronScan、TronLink 风格授权
js/classroom.js课堂层8 检查点、证据标注、教师面板、复盘报告、技术原理

一条消息长什么样

// data.js 里的订单卡（简化） { id: 'g10', sender: 'mallbot', via: '@yunshang_bot', card: 'order', order: { id: 'YS20260822-0731', product: '新人体验卡', price: '1.30', status: '待支付' }, buttons: [[{ text: '💳 立即支付', action: 'pay:open', webapp: true }]], }

按钮点击怎么变成下一步

// ui.js：所有按钮共用一条事件委托 document.addEventListener('click', (e) => { const btn = e.target.closest('[data-action]'); if (!btn) return; btn.classList.add('loading'); // 模仿 answerCallbackQuery 的转圈 TG.flows.run(btn.dataset.action, { msg: btn.dataset.msg }); }); // flows.js：action 路由 if (action === 'pay:open') { openPay(ctx); } if (action === 'okpay:claim') { claim(); } if (action === 'okpay:bind') { bindPage(); }

这对应真实 Telegram 的 callback_query：按钮把 data 交给 bot 服务器；服务器执行逻辑，再 editMessageText 更新同一条消息。仿真里的「输入中…」和延迟，是在模仿 bot 的网络往返。

仿站与钱包怎么模拟

TG.openBrowser({page:'pay'}) 会打开一个全屏 overlay，更新 URL 栏，渲染 payPage()；TG.openWallet({kind:'approve'}) 打开 TronLink 风格弹窗，展示「授权对象 / 授权额度 / 矿工费 / 合约 / 原始请求」。点「确认授权」不会发任何交易，只调用本地 flows.run('web:approved')，把 flags.approved 置为 true，并让复盘记录「签了无限额度」。这就是为什么仿真可以安全地演示「被盗」——它只改变本地状态。

仿真里没有：真实 Bot Token、真实群、真实钱包、真实 RPC、真实签名、真实转账。域名、地址、合约、余额都是道具；报告页也会明确标注。
08

怎么安全复现

复现分三层：界面层（本仿真）、Telegram 入口层（WebApp / bot）、链上层（测试网）。不要在主网、不要用真实受害者、不要部署钓鱼站。

A. 本地仿真（已经做好）

双击 index.html 即可。所有页面、按钮、状态机、复盘都在本地；适合课堂投影和学生分组操作。

B. 真实 Telegram 入口

把仿真部署到 HTTPS（Cloudflare Pages / GitHub Pages / Vercel），用 @BotFather 建 bot，配置 /newapp 或 setChatMenuButton 为 Web App。学生在真实 Telegram 里点按钮进入。注意：web_app 按钮只在私聊有效；群里用普通 url 按钮。

C. 测试网复现授权

用 TRON Nile 测试网和测试 USDT，两个测试钱包：A 授权 B（或一个测试合约）一定额度；B 调 transferFrom；观察 Approval / Transfer 事件；最后 A 用 approve(spender, 0) revoke。全程测试币，不接触主网。

不做的事：不提供可部署的钓鱼站、drainer 合约、归集器或批量账号脚本；不用真实用户做实验；不在主网验证。技术拆解的目的是识别与防御，不是复刻犯罪工具。

D. 课堂演示顺序

先让学生走仿真 → 打开复盘看 8 个检查点 → 教师开「技术原理」讲 approve → 打开「后台视角 + 快进 3 天」看归集 → 最后在测试网/区块浏览器上看真实的 Approval 事件（只读，不签名）。
