后台与监控：从一条 callback 到一次归集

左边仿真里的每一次点击，后台都会落到几个固定组件：bot 服务、数据库、索引器、规则引擎、队列、worker、归集地址、操作员 bot。这一页把每一段用代码段写清楚。

边界：这是识别与防御材料，不是可部署的盗币工具。Telegram、数据库、索引、规则、撤销都是可运行/可防御代码；构造并签名 transferFrom 的那一步故意用 NotImplementedError 占位，不提供可运行实现。
打开左右对照，点「后台代码」 看链上机制 看受害者的每一页

01 总架构：一条点击，七个组件

先看数据怎么流，再看每一段代码。不要把“后台”想成一个黑箱，它是一条流水线。

[Telegram Bot API] │ webhook / long poll ▼ [bot 服务] ──写──▶ [users / orders / callbacks / approvals] │ ├─▶ [dapp 前端] bind / pay / verify ├─▶ [queue] ──▶ [worker] ──▶ (攻击步骤：省略) ──▶ [collector] └─▶ [operator bot] alerts ▲ [索引器] ──读── [TronGrid / 全节点] ──▶ Approval / Transfer
组件职责在骗局里的作用
bot 服务收 update、回消息、改消息、发按钮把“点击”变成数据库里的状态
dapp 前端仿站绑定/收银/验资页把“提现”包装成连接/授权
数据库用户、订单、回调、授权、任务维持“平台余额/订单状态”的假账
索引器读 Approval / Transfer知道谁授权了、谁进钱了
规则引擎按额度、spender、余额打分决定先盯谁、何时动手
队列/worker异步重试、状态机把“监控”变成可批量执行
操作员 bot通知、看板让人不用盯链也能收割

02 Telegram webhook：点击先落库

bot 不需要“很聪明”，它只需要可靠地收 callback、去重、入队。

webhook.py · 收 callback，幂等入队python
@app.post("/tg/{secret}")
async def tg(secret: str, update: dict):
    if not hmac.compare_digest(secret, BOT_SECRET):
        raise HTTPException(status_code=403)

    if "callback_query" in update:
        cq = update["callback_query"]
        # 同一个 callback_query.id 只处理一次
        if not await db.claim_callback(cq["id"]):
            return {"ok": True}
        await queue.enqueue("callback", {"id": cq["id"], "data": cq["data"]})
        await bot.answer_callback_query(cq["id"])

    return {"ok": True}
  • secret：webhook URL 里带密钥，防止别人伪造 update；生产还要校验来源 IP/签名。
  • callback_query.id：同一个点击可能重投；claim_callback 用唯一键保证只处理一次。
  • answerCallbackQuery：不回应，客户端按钮会一直转圈；这是“像正常机器人”的细节。
  • 入队：webhook 只做轻量写库，耗时动作交给 worker，避免 Telegram 超时重投。
受害者看到的“秒回/按钮变了”，背后是 editMessageText + callback；不是链上确认。

03 数据表：假账、真事件、任务

后台至少有三类数据：平台假账、链上事件、待执行任务。三张表不能混。

schema.sql · 最小表结构sql
create table if not exists users (
  tg_id      bigint primary key,
  username   text,
  created_at timestamptz default now()
);

create table if not exists orders (
  id         text primary key,
  user_id    bigint references users(tg_id),
  amount     numeric(18,6) not null,
  status     text not null,          -- created / pending / paid / shipped
  created_at timestamptz default now()
);

create table if not exists approvals (
  txid       text not null,
  log_index  int  not null,
  owner      text not null,
  spender    text not null,
  value      numeric(78,0) not null,
  block_ts   timestamptz,
  primary key (txid, log_index)       -- 幂等键
);

create table if not exists jobs (
  id         bigserial primary key,
  kind       text not null,
  payload    jsonb not null,
  status     text not null default 'queued',
  attempts   int  not null default 0,
  unique (kind, (payload->>'key'))
);
  • orders：订单状态是 bot 写的，不是支付机构回调；paid 可以是前端/客服手动改。
  • approvals：主键 (txid, log_index) 是幂等键；同一条事件重复扫不会重复入账。
  • jobs：unique(kind, payload->>'key') 防止同一授权被重复排队。

04 Approval / Transfer 解码：事件才是真的

TRC20 的授权和转账都会发事件。看懂 topic 和 data，就不需要“猜”页面。

decode.py · 只读解析事件python
APPROVAL_TOPIC = "0x8c5be1e5ebec7d5bd14f71427d1e84f3dd0314c0f7b2291e5b200ac8c7c3b925"
TRANSFER_TOPIC = "0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef"
USDT_DECIMALS  = 6

def addr(topic: str) -> str:
    return "0x" + topic[-40:]

def decode_approval(log: dict) -> dict:
    return {
        "owner":   addr(log["topics"][1]),
        "spender": addr(log["topics"][2]),
        "value":   int(log["data"], 16),
    }

def decode_transfer(log: dict) -> dict:
    return {
        "from":  addr(log["topics"][1]),
        "to":    addr(log["topics"][2]),
        "value": int(log["data"], 16) / 10 ** USDT_DECIMALS,
    }

接口声明（只声明，不实现；这就是钱包弹窗和 transferFrom 对应的函数形态）：

IERC20.sol · 只声明接口solidity
interface IERC20 {
    function approve(address spender, uint256 amount) external returns (bool);
    function allowance(address owner, address spender) external view returns (uint256);
    function transferFrom(address from, address to, uint256 amount) external returns (bool);
}
  • topic[0] 是事件签名哈希；Approval(address,address,uint256) 和 Transfer(address,address,uint256) 是固定值。
  • topic[1]/[2] 是 indexed 地址，取后 40 个 hex 字符；data 是额度/金额。
  • USDT 是 6 位小数；1000000 = 1 USDT，不要按 18 位算。
  • Approval 不产生 Transfer：授权时余额不变，所以受害者当时看不到“被扣”。

05 索引器：轮询、确认数、游标

监控不是“盯着一个页面”，是持续读链上事件，并且知道读到哪。

indexer.py · 按时间游标轮询 Approvalpython
def poll_approvals(cursor_ts: int):
    while True:
        r = requests.get(
            f"https://api.trongrid.io/v1/contracts/{USDT}/events",
            params={
                "event_name": "Approval",
                "only_confirmed": "true",
                "limit": 200,
                "min_block_timestamp": cursor_ts,
                "order_by": "block_timestamp,asc",
            },
            headers={"TRON-PRO-API-KEY": API_KEY},
            timeout=20,
        )
        r.raise_for_status()
        rows = r.json().get("data", [])
        if not rows:
            break
        for log in rows:
            yield log
        cursor_ts = int(rows[-1]["block_timestamp"]) + 1
  • only_confirmed：只取已确认事件；否则链上回滚会让任务重复/错乱。
  • 游标：min_block_timestamp 记录上次位置；进程重启从游标继续。
  • 分页/限流：TronGrid 有速率限制；失败要指数退避，不能死循环。
  • 全节点/WebSocket：也可以用事件插件或 WebSocket 订阅；原理相同，仍要处理确认数和重连。
  • reorg：确认数不足时先不执行；记录 block/txid，发现回滚要能撤销任务。

06 规则引擎：先盯谁

不是每个授权都值得动手；规则引擎按“无限额度、陌生 spender、余额”打分。

rules.py · 打分与分流python
MAX_UINT256 = 2 ** 256 - 1

def score(approval: dict, balance: float, known: set[str]) -> int:
    s = 0
    if approval["value"] == MAX_UINT256:      s += 50  # 无限额度
    if approval["spender"] not in known:      s += 20  # 陌生 spender
    if balance > 30:                          s += 30  # > 30 USDT
    return s

def decide(approval, balance, known):
    s = score(approval, balance, known)
    if s >= 60:
        queue.enqueue("sweep", {"key": approval["txid"]})
    else:
        queue.enqueue("alert", {"key": approval["txid"]})
  • 无限额度（2^256-1）是最强信号：一次授权，长期可转。
  • spender 不在已知集合，加分；真实场景还会看合约创建时间、是否开源、历史调用。
  • 余额决定“现在有没有肉”；没有余额就继续监控，等进钱。
  • 分数阈值是策略，不是法律；防御方也可以用同一套规则给自己报警。

07 队列与 worker：攻击步骤故意省略

后台的“自动化”体现在队列：状态、重试、幂等、死信。真正转币的那一步不提供。

worker.py · 只保留告警分支python
def worker(job):
    if job.kind == "alert":
        notify_operator(job.payload)
        return

    if job.kind == "sweep":
        # 攻击步骤：这里会构造并签名 transferFrom。
        # 本材料不提供可运行实现，避免被直接用于盗币。
        raise NotImplementedError("educational only")
  • 状态机：queued → running → done / failed；失败重试要有上限。
  • 幂等：同一 txid 只能有一个 job；重试不能重复转。
  • 死信：多次失败进 dead letter，人工看，避免无限重试。
  • 省略：sweep 分支里的 transferFrom 构造/签名/广播不写；这是直接盗币能力。
从防御角度：如果看到“授权后余额不变、过几天才被转走”，对应的就是这条异步流水线。

09 防御：查授权、撤销、再监控

同一套事件和额度，可以用来保护自己。这一段是可运行的防御代码。

revoke.js · TronWeb 撤销授权javascript
const allowance = await usdt.allowance(owner, spender).call();

if (!allowance.isZero()) {
  const tx = await usdt.approve(spender, 0).send({
    feeLimit: 100_000_000,
  });
  console.log("revoked", spender, tx);
}
  • 定期查自己地址的 Approval，重点看无限额度、陌生 spender。
  • 发现异常先 approve(spender, 0)；再把剩余资产转到新地址。
  • 撤销只停未来，不追回已经转走的；越早越好。

10 监控原理：事件、确认、幂等、限流

  • 事件驱动：监控 Approval（授权发生）和 Transfer（资金移动），不要只盯页面余额。
  • 确认数：只对已确认事件执行；不同链/节点确认策略不同，Tron 也要考虑回滚。
  • 幂等：(txid, log_index) 唯一键；队列按 key 去重；重试不重复执行。
  • 游标：记录最后处理的时间/区块；重启可续；分页用 fingerprint/下一页。
  • 限流/退避：API 有速率限制；429/5xx 指数退避；失败进死信。
  • 误报：正常 dapp 也会授权；用 spender 白名单、额度、余额、人工复核降噪。
  • 防御监控：给自己地址配同样的规则；无限额度/陌生 spender 直接告警。
骗子的“监控”不是看受害者手机，是看链上公开事件；你的授权一旦上链，所有索引器都能看到。

12 防御清单

  1. 任何“提现/验资/绑定”要求 approve 的，默认拒绝。
  2. 看到“无限额度”直接拒绝；不确认 spender 不签。
  3. 日常钱包只放小额；大额放冷钱包/多签。
  4. 定期查自己的 Approval；发现异常先 revoke，再转移剩余资产。
  5. 不点聊天里的支付链接；先看域名/证书/WHOIS。
  6. 已经签了：保留 txid、截图、聊天记录，报案；不再补钱。
